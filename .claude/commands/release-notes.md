# リリースノート変換

内部スプリントリリースノートを（Slack `#aem-sites-optimizer-announcements` チャネルまたは`.cursor/commands/release-notes` カーソル出力から）お客様向けのエントリに変換し、`help/documentation/release-notes.md`に追加します。

## 使用方法

このスキルを呼び出し、プロンプトが表示されたら、内部リリースノートのコンテンツを貼り付けます。 スキルは：

1. フィルタリングとトーンのルールについては、以下のガイドラインを適用します。
2. 内部リリースノートを解析します（絵文字で分類されたセクション：✨機能、🚀拡張機能、🤖 AI ファースト、🔧修正、🏢 BackOffice）。
3. ガイドラインごとに、除外されたすべてのカテゴリをフィルタリングします（AI ツール、BackOffice、ローカライゼーションリンター、E2E テスト、SitesInternal専用アイテム）。
4. 次のトーンの例を参照して、顧客向けのトーンの残りの項目を書き換えます。
5. 関連項目を機能領域ごとにグループ化します（チームまたはリポジトリ別ではありません）。
6. 以下のページ構造テンプレートに従って、新しいリリースエントリとしてフォーマットします。
7. 新しいエントリの先頭に`help/documentation/release-notes.md`を付けます（前の最新エントリの上、ページのイントロパラグラフの下）。
8. アイテムの保持、アイテムの書き換え、アイテムの削除（各アイテムの理由を含む）を示す概要テーブルを印刷します。

## ガイドライン

### 基本原則

1. **お客様のメリットを最初に受け取ります。** すべてのエントリは、「以前は不可能だった今できることや、改善できることは何か」という質問に答える必要があります。 — 「何を出荷したんですか？」ではなく 実装ではなく価値をもってリード。

2. **リーダーシップのトーン。** 意思決定者のために書く：技術的な力学ではなく、結果と能力。 デジタルエクスペリエンス担当バイスプレジデントは、アップデートが重要な理由をすぐに理解する必要があります。

3. **内部用語はありません。** すべてのチーム内省略形を置き換えます。
   - 「PLG」→「体験版ユーザー」または「新規顧客」
   - 「BackOffice」→完全に省略される（インフラストラクチャのみの変更）
   - &quot;MSM&quot; → &quot;AEM Multi-Site Manager&quot;
   - &quot;SHM&quot; → &quot;Site Health Monitor&quot;
   - &quot;OrcaFix&quot;, &quot;Cursor commands&quot;, &quot;AGENTS.md&quot;→完全に省略される
   - 「EDS」 → 「Edge Delivery Services」

4. **短いエントリ。** *what*&#x200B;の1文、*why it matters*&#x200B;の1文。 両方が1つの文に収まる場合は、それを行います。

5. **正確な範囲。** 顧客が製品UIやエクスペリエンスで見ることのできる変更のみをワークフローに含めます。 インフラストラクチャ、ツール、開発者エクスペリエンスの変更は除外されます。

6. **早期アクセス機能にフラグを付ける。** デフォルトでオフになっている機能フラグの背後に機能が搭載されている場合（例：LaunchDarkly `FeatureGate`/`isEnabledByDefault={false}`）、太字の機能名に`(Early Access)`を追加します。これは、段階的機能に使用される既存の`(General Availability)`規則を反映しています。 不明な場合は、すべての顧客に対してデフォルトで機能がオンになっているかどうかを確認します。オンになっていない場合は、早期アクセスです。 コードのデフォルトの機能フラグに照らし合わせて検証します。推測しないでください。

### ページ構造テンプレート

各リリースエントリは、次の構造に従います。

```markdown
## [Month Start]–[Day End], [Year]

### New Features

- **[Feature Name]** — [One-sentence benefit statement. One sentence of business context if needed.] (append `(Early Access)` or `(General Availability)` to the feature name when the feature's availability status is notable)

### Enhancements

- **[Enhancement Name]** — [One-sentence improvement statement.]

### Bug Fixes

- [Short description of what was fixed and why it matters to users.]
```

**ルール：**
- 日付範囲の形式：`May 11–22, 2026` （en-dash、省略形の月、4桁の年）。
- 逆順：ページ上部の最新リリース。
- コンテンツがあるセクションのみを含めます。 空の場合は、「機能強化」または「バグ修正」を省略します。
- バグ修正エントリでは、太字の機能名は使用されません。これらは単純な箇条書きです。
- 3つ以上のユーザーに表示される修正が注目に値する場合にのみ、バグ修正を含めます。

### 含める内容と除外する内容

**含める：**

| カテゴリ | 例 |
|---|---|
| 新しい商談タイプ | Ad Intent Mismatch, No CTA Above the Fold |
| 新しいビューやワークフロー | デプロイ済みタブ、CSV書き出し、Jira リンク |
| 体験版/オンボーディングの改善 | ガイド付きの設定フロー、オンボーディングなし |
| 設定の改善 | ターゲット URLの監査、配信タイプ設定 |
| 有意義なUXの修正 | 不適切なカウント、壊れたナビゲーション、意思決定に影響を与える表示の問題 |
| 新しいデータ/統合 | オーガニック検索のAhrefs データ、セキュリティの依存ツリー |
| オーサーへのデプロイ機能 | 直接展開をサポートする新しい商談タイプ |

**除外：**

| カテゴリ | 理由 |
|---|---|
| AI ツール（OrcaFix、Cursor コマンド、AGENTS.md、Claude Code ルール） | 社内開発者ツール、顧客には表示されない |
| ローカライゼーションリンター/プリコミットフック | 製品機能ではなくエンジニアリングプロセス |
| バックオフィス/インフラストラクチャの変更 | エンドユーザーの動作を変更しない限り、UIに表示されない |
| React Spectrum バージョンのアップグレード | ユーザーに表示されない内部依存関係 |
| E2E テストの改善 | 製品の機能ではなく、エンジニアリング品質 |
| リリースパイプラインの自動化 | 内部プロセス |
| SitesInternal-only機能 | お客様が利用できない |

### トーンの例

| 内部フレーズ | 顧客向けのフレーズ |
|---|---|
| 「手動検証ワークフローのREJECTED状態が導入されました」 | 「提案を拒否としてマークして、提案がサイトに適用されないことを示すことで、商談リストを実用的なアイテムに集中させることができます。」 |
| 「正規表現とHreflangの機会のデプロイドビュー（日付別にグループ化）」 | 「CanonicalおよびHreflangの機会に対する変更は、「デプロイ済み」タブでデプロイメント日ごとにグループ化され、何がいつ修正されたかを明確に把握できるようになりました。」 |
| &quot;Alt Text Autofix V2 — &#39;修正可能性の確認&#39; pre-flight assessment&quot; | 「代替テキスト修正をデプロイする前に、フライト前チェックを実行して、修正がコンテンツに正常に適用できることを確認できます。」 |
| 「SHM指標に対するストレージの96%最適化」 | omit — インフラストラクチャのみ |
| 「AGENTS.mdと正式な担当者の役割と安全ガードレール」 | omit – 内部AI ツール |
| 「E2E テストのパフォーマンス最適化（6分→～5分）」 | omit — エンジニアリング・プロセス |

### グループ化ルール

- **チームまたはリポジトリではなく、機能領域**&#x200B;でグループ化します。 例えば、すべての代替テキストの機能強化（機能、機能強化、修正）は同じ領域に属しており、セクション間で分散しません。
- **密接に関連する修正**&#x200B;を個別にリストするのではなく、単一の箇条書きに統合します（例：「有料トラフィック、アクセシビリティ、セキュリティの機会をまたいだ複数の表示とレイアウトの改善」）。
- **バグ修正のしきい値セクション**：このセクションは、ユーザーに表示される修正が3つ以上ある場合にのみ含めます。 この閾値を下回る軽微または純粋に化粧品の修正は省略されるべきである。

## 手順

1. このファイルでガイドラインを適用する – すべての原則、含める/除外ルール、トーンの例、グループ化ルールを内部化します。
2. 対象となる日付範囲（例：「2026年5月11日～22日」など）が指定されていない場合は、ユーザーに連絡します。
3. 内部リリースノートの内容を貼り付けるか、ファイルパスを承認するかをユーザーに尋ねます。
4. コンテンツの処理：
   - **各セクション （✨/🚀/🤖/🔧/🏢）とその箇条書きポイントを**&#x200B;解析します。
   - 上の除外テーブルごとに&#x200B;**フィルター**。 ドロップされた各項目に理由を付けます。
   - **書き換え**&#x200B;は、ユーザーのトーンに沿った項目を維持しました。メリット優先、専門用語なし、短いエントリです。
   - 複数のアイテムが関連する機能領域ごとに&#x200B;**グループ**。
   - **しきい値チェック**: ユーザーに表示される修正が3つ以上ある場合にのみ、「バグ修正」セクションを含めます。
5. 上記のページ構造テンプレートを使用して、新しいエントリを書式設定します。
6. `help/documentation/release-notes.md`の現在のコンテンツを読み取ります。
7. ページのイントロ段落の直後（前の最新の`##`日付見出しの前）に新しいエントリを挿入します。
8. 更新したファイルを書き込みます。
9. 概要テーブルを印刷します。

## 入力形式

このスキルは、標準チーム形式の内部リリースノートを受け入れます。

```
*ASO UI Release Notes — [Date Range]*
Collaborators: [teams]

✨ *Features*
• [Feature description]

🚀 *Enhancements*
• [Enhancement description]

🤖 *AI-First Development*
• [AI tooling items — will be dropped]

🔧 *Fixes & UX Improvements*
• [Fix description]

🏢 *BackOffice*
• [BackOffice items — will be dropped]
```

## 出力

スキルの出力：

1. 書式設定された顧客向けエントリ（書き込み前のレビュー用）。
2. `release-notes.md`を変更する前に確認を求めるメッセージが表示されます。
3. 書き込み後：保存/書き換え/削除されたアイテムのサマリーテーブル。
